== Abstract

Neo-Modus Direct Connect (NMDC) is a text protocol for a client-hub network.
The same protocol structure is used both for client-hub and client-client communication.
This document is split into two parts; the first shows the structure of the protocol, while the second implements a specific system using this structure.

NMDC was written by Jon Hess, in the implementation of the (proprietary) NMDC client and hub software, but was never documented.
The protocol was reverse-engineered later on by others, and soon followed open implementations.
Extensions have followed over the years and may be incompatible with the original NMDC software.

== Protocol

=== General

* Most messages begin with a ($) - a dollar sign
* Most messages end with a (|) - a pipe
* Command names and parameters use single space ( ) and additional dollar signs as separators
* There is no standardization on code page to use. The local charset of the computer system is commonly used. The original implementation used Windown-1252/CP1252.
* Hub port defaults to 411. The client should then try 412, 413 etc.
* Client port defaults to 412
* Some command names are incorrectly spelled, per the original protocol. This document notes when a spelling error is _intentional_, per the original protocol.
* The hub should validate that the client sending the message is actually the correct user
* This document does not mainly use (<) and (>) brackets for illustration purposes; any occurrence should be taken literally, unless otherwise noted
* This document use ([) and (]) square brackets for optional data; any literal occurrence will be noted as such
* State is *Handshake* when handshake is in progress. State is *Connected* when handshake is completed. State can also be *Both*. Commands that apply to specific state can't be exchanged in different state, except *Both*.

There are different types of routed messages:

[options="autowidth"]
|=====
|Client - Hub
|Client - Hub - Client
|Hub - Client
|Hub - Hub
|Hub - Hublist
|Hub - Pinger
|Pinger - Hub
|=====

==== Status messages

Most clients send a chat message to all users to indicate that a user has been kicked.
That is, if a client A kicks client B, client A will send out a message to client C and D to indicate that the client B is kicked.
To avoid being potentially flooded by this message, clients have implemented a de facto message to indicate kicks.

====
 <john> is kicking peter because: i am not a dog person|
====

The key aspect here is the two phrases "is kicking" and "because:".
Including these two parts, regardless of the other content, will cause most clients to show the message as a status bar message.

Note that the hub will not actually treat this as a kick.

==== Reference to hub in $Lock

[[reference_lock]]

To identify the source of the hub in a client-client connection, some clients add a reference to the hub in the *$Lock* that is sent, where the information is placed in the *Pk* parameter.

This information can also be provided in a client-hub connection.

Example:

====
 $Lock EXTENDEDPROTOCOLABCABCABCABCABCABC Pk=DCPLUSPLUS0.882Ref=example.com:411|
====

==== Escape sequences

There are two ways protocol delimiters are displayable (dollar sign, pipe etc);

===== Method 1

By using "/%DCNXXX%/" where "XXX" is the decimal number for an ASCII character.

This escape sequence method is used by all implementations for the *$Key*/*$Lock* sequence (see below).
This is also used by multiple implementations for normal viewing purposes (e.g. in a chat message).

This escape sequence predates the second method listed below.

The following escape sequences exist for this method:

[options="autowidth,header"]
|=====
|Escape sequence |Description
|/%DCN000%/ |0x0A, null character, not allowed anywhere in the protocol
|/%DCN005%/ |Enquiry character, used by some commands
|/%DCN036%/ |$, dollar sign, used by almost all commands
|/%DCN096%/ |`, grave accent
|/%DCN124%/ |\|, pipe, used at end almost all of commands
|/%DCN126%/ |~, tilde
|=====

Example:

====
 <john> i am going to display a dollar sign /%DCN036%/ and then a pipe /%DCN124%/.|
====

===== Method 2 (most common)

By using the HTML equivalent of the character.

This escape sequence was created in and is used by DC++.

Note that DC\++ uses the first method for the *$Key*/*$Lock* sequence.
DC++ uses this method for displayment purposes (e.g. chat messages).

The following escape sequences exist for this method:

[options="autowidth,header"]
|=====
|Escape sequence |Description
|\&#36; |$, dollar sign, used by almost all commands
|\&#124; |\|, pipe, used at end of almost all commands
|\&amp; |&, ampersand
|=====

Example:

====
 <john> i am going to display a dollar sign &#36; and then a pipe &#124;.|
====

==== $Key/$Lock sequence

After the first NMDC client and hub was introduced, others began to create their own implementation of the NMDC protocol.
The original NMDC client and hub was freeware but not open source.
In a way to combat other implementations, the author of the protocol decided upon a way to restrict the other implementations by a pseudo-cryptographic key exchange.

This exchange is typically referenced as a pseudo-Diffie-Hellman key exchange for its similarity, although they are not equivalent.

The *$Key* and *$Lock* commands are not listed as extensions as they exist in at least NMDC hub 1.0.25 and NMDC client 1.0 Preview Build 9.1.

=== Security Considerations

==== Distributed Denial of Service Potential

The ongoing operation of NMDC's peer to peer connections provides opportunities for both malicious clients on certain hubs and malicious hubs to coordinate clients of those hubs in connecting en masse to an arbitrarily specified IP address and port.
Hubs _SHOULD_ mitigate this risk by only relaying such connection requests when it can verify that the IP addresses and ports contained therein belong to clients initiating such peer to peer connection requests.
Clients _SHOULD_ effect similar amelioration through both attempting to reconnect only to hubs to which they have initially connected once and by providing upon connection referrer information regarding which hub has relayed to them the IP and port to which they are connecting.

See also <<reference_lock,Reference to hub in $Lock>>.

==== Case-sensitivity Mismatches and Duplicated Shares Entries

Both accidentally due to differences in filesystem case-sensitivity assumptions and intentionally by malicious clients can arise filelists containing either entires either entirely or up to case identical.
Client software _SHOULD_ detect these cases and avoid wasteful downloading.

==== Filelist Processing Memory Usage

The BZip2-compressed filelists that NMDC URIs ending in a separator are required to process potentially expand due to malicious construction to cause a processing client to exhaust its memory or address-space capacity.
Likewise, even non-malicious filelists can grow arbitrarily large such that in combination with other memory requirements of client software, similar exhaustion occurs.
Client software therefore _SHOULD_ bound BZip2 decompression memory usage and use streaming XML APIs to process filelists.

See https://dcpp.wordpress.com/2010/03/12/dc-0-75-and-older-vulnerable-to-bzip2-filelist-bomb/[DC++ 0.75 and older vulnerable to BZip2 filelist bomb] for more information.

==== Excessive Local Storage Consumption

The ZLib compression supported by NMDC for client-client transfers permits construction of transferred data which consume disk space substantially more rapidly for the downloading client than network bandwidth would indicate.
Client software _SHOULD_ monitor downloads for impending storage capacity limits with a view to prevent local denials of service resulting from exceeding them.

=== Commands

==== <Chat>

====
 <_nick> _message|
====

Contexts: Client -> Hub -> Client, Hub -> Client

Will send a public chat *_message* by *_nick*.
The hub should broadcast the message to all clients including the sender.

Note: This command does _NOT_ start with a dollar sign ($), the brackets (<) and (>) are required.
Some implementations allow spaces in the nickname, be aware that other implementations may simply search for the first occurrence of a space.

If the chat message contain special protocol characters, they _MUST_ be replaced by its HTML equivalent as mentioned earlier.

Example:

====
 <john> cats are cute|
====

==== $To:

====
 $To: _other_nick From: _nick $<_nick> _message|
====

Contexts: Client -> Hub -> Client, Hub -> Client

Will send a private message from one user to another user.
The same rules as a basic chat message apply.

Note: The colon (:) at the end of command, it must be present.

Example:

====
 $To: john From: peter $<peter> dogs are more cute|
====

==== $ConnectToMe

====
 $ConnectToMe _remote_nick _sender_ip:_sender_port|
====

Contexts: Client -> Hub -> Client

Request that *_remote_nick* connect to the sending user for an active TCP connection for file transfers.
Clients sending this must allow incoming TCP connections.
There is no default port, though 412 was mentioned in general section.

Example:

====
 $ConnectToMe john 192.168.1.2:412|
====

Note that the above is for older clients.

Newer versions of NMDC client include the sender's nick as well (but may not be compatible with all implementations);

====
 $ConnectToMe _sender_nick _remote_nick _sender_ip:_sender_port|
====

Example:

====
 $ConnectToMe peter john 192.168.1.2:412|
====

==== $RevConnectToMe

====
 $RevConnectToMe _sender_nick _remote_nick|
====

Contexts: Client -> Hub -> Client

Request that the *_remote_nick* send a *$ConnectToMe* back to *_sender_nick*.
Clients sending do not allow incoming TCP connections whereas the remote user does (or should).

Example:

====
 $RevConnectToMe peter john|
====

==== $Ping

====
 $Ping _sender_ip:_sender_port|
====

*_sender_ip* is the IP address of the remote client.
*_sender_port* is the port of the remote client that is being listened to.

==== $GetPass

====
 $GetPass|
====

Contexts: Hub -> Client

Request that the client send a password that correspond to a user account matched by the user's nick name.

==== $MyPass

====
 $MyPass _password|
====

Contexts: Client -> Hub

Providing the password in plain text to the hub after a request.
Implementations should be aware of potential pipe and dollar signs in the password.

Example:

====
 $MyPass qwerty|
====

==== $LogedIn

====
 $LogedIn _nick|
====

Contexts: Hub -> Client

Sent to users who successfully log in.
Note that the message should only be sent to operators.
Note that some implementations do not use this command.
The spelling of this command is not a mistake.

Example:

====
 $LogedIn john|
====

==== $Get

====
 $Get _file$_offset|
====

Contexts: Client -> Client

*_file* is the remote location including path of the file.
*_offset* is the byte offset to start at for resuming files.

Example:

====
 $Get C:/Uploads/myfile.txt$15|
====

==== $Send

====
 $Send|
====

Contexts: Client -> Client

This is used as a way to specify that the file should be sent.
The uploader should proceed to stream the amount of bytes requested previously.

==== $FileLength

====
 $FileLength _file_size|
====

Contexts: Client -> Client

This command is used as a way to provide the size of the file requested.

==== $GetListLen

====
 $GetListLen|
====

Contexts: Client -> Client

Get file list size.

==== $ListLen

====
 $ListLen _file_size|
====

Contexts: Client -> Client

This command is used as a way to provide the size of the file list of the client.

==== $Direction

====
 $Direction _direction _number|
====

Contexts: Client -> Client

This command is used as a way to decide which party should be allowed to download.

The direction is either "Upload" or "Download", depending on whether the connection request is a *$ConnectToMe* or *$RevConnectToMe*.

The number is a random number above zero "0", typically between "1" and "32767".
If both clients want to download, the client with the highest number gets to start downloading first.
If the numbers are equal, the connection is closed.

This command should be sent;

* After a *$Key* command or
* After a *$Lock* command with "EXTENDED" information

If the *$Lock* is "EXTENDED", *$Direction* _MUST_ be sent after the *$Lock* command and not the *$Key* command.

Implementation note: The highest number DC++ sends is "32767" (2^15-1, 0x7FFF) as the Neo-Modus Direct Connect client will disconnect if it receives a higher number.
Clients can send a higher value, in risk of losing compatibility.

Implementation note: A potential bug, that may be fixed, in DC++ revolved around the following circumstance;

* Client A has zero free slots
* Client B has free slots (doesn't matter how many)
* Client A and client B want a file from one another
* Client A loses the random number "battle"

Client B will not get a slot because of client A does not have any slots available.
DC++'s status bar of client B will say "Connecting..." instead of saying "No slots available" that is the de facto message.
A suggested patch involve "cheating"; client B will use a high random number after it has lost and will return to normal when it has won.

==== $Cancel

====
 $Cancel
====

Contexts: Client -> Client

This command is used as way to indicate that the transfer of a file should be cancelled prematurely.

This command is sent by the downloader.
When the uploader receives the message, it should stop sending data followed by a *$Canceled*.
It is possible that some implementations continue to send some data after the *$Cancel* and *$Canceled*; the downloader should discard this data.

This command was only implemented in NMDC v.1 and not in subsequent version or in other clients.

Note: There is no pipe (|) at the end of this command.

==== $Canceled

====
 $Canceled
====

Contexts: Client -> Client

This command is used as way to indicate that the transfer of a file was cancelled prematurely.

This command is sent by the uploader.

This command was only implemented in NMDC v.1 and not in subsequent version or in other clients.

The spelling of this command is not a mistake.

Note: There is no pipe (|) at the end of this command.

==== $BadPass

====
 $BadPass|
====

Contexts: Hub -> Client

Indicates that the supplied password is invalid.
The client shall be immediately disconnected after this message is sent.

==== $HubIsFull

====
 $HubIsFull|
====

Contexts: Hub -> Client

Indicates that the hub has reached its maximum amount of users and will not accept additional users.

==== $ValidateDenide

====
 $ValidateDenide _nick|
====

Contexts: Hub -> Client

The requested nick name is already taken by or is reserved for another user.
The spelling of this command is not a mistake.

Example:

====
 $ValidateDenide john|
====

==== $MaxedOut

====
 $MaxedOut|
====

Contexts: Client -> Client

Sent by a client to another when there are no more slots available upon request of files.

See the *QP* extension for an extended *$MaxedOut*.

==== $Failed

====
 $Failed _message|
====

Contexts: Client -> Hub, Client -> Hub -> Client, Client -> Client, Hub -> Client

General purpose fail command.
Implementations may use this command to signify files that are not available.
*$Failed* is usually sent in response to a *GetZBlock*, *UGetBlock* and *UGetZBlock*.

==== $Error

====
 $Error _message|
====

Contexts: Client -> Hub, Client -> Hub -> Client, Client -> Client, Hub -> Client

General purpose fail command.
Implementations may use this command to signify files that are not available.
*$Error* is usually sent in response to a *GetZBlock*, *UGetBlock* and *UGetZBlock*.

When this command is sent in context of hub to client, and message equals to *CTM2HUB*, it means that client connection was made to a hub, and client must instantly stop trying to connect to address previously requested in CTM.

Example client request:

====
 $ConnectToMe john 192.168.1.2:411|
====

Once client connects to 192.168.1.2:411, it receives *$Error* command:

====
 $Error CTM2HUB|
====

Hub softwares currently known to support this command: Verlihub

==== $Search

====
 $Search _ip:_port _search_string|
 $Search Hub:_nick _search_string|
====

Contexts: Client -> Hub -> Client

The former is sent by active clients and the latter for passive clients.
The IP is the client's own IP address and the port is an open UDP port that accept incoming UDP traffic.
"Hub" should be taken literally.
The nick is the nickname of the searching user.

===== Search string

The string describing the file or directory the client is searching for.
It is made up of a question mark (?) delimited string as follows:

====
 _size_restricted?_is_max_size?_size?_data_type?_search_pattern
====

*_size_restricted* is "T" if the search should be restricted to files of a minimum or maximum size, otherwise "F".

*_is_max_size* is "T" if the size restriction places an upper limit on file size, "F" if it places a lower limit.
If *_size_restricted* is "F", *_is_max_size* has no meaning and can be either "F" or "T"; DC++ sends "T" in TTH searches, see the example below.

*_size* is the minimum or maximum size of the file to search for (according to *_is_max_size*) if *_size_restricted* is "T", otherwise zero "0".

*_data_type* restricts the search to files of a particular type.
It is an integer selected from:

* 1 - Any files
* 2 - Audio files
* 3 - Compressed files
* 4 - Document files
* 5 - Executable files
* 6 - Picture files
* 7 - Video files
* 8 - Folders
* 9 - TTH hash

*_search_pattern* is used by other users to determine if any files match.
If it is a TTH search, *_search_pattern* should be "TTH:<hash>".

Spaces in the search pattern are replaced by a dollar sign ($).
As with all NMDC messages, ($) and (|) are escaped with "\&#36;" and "\&#124;", with (&) being further replaced with "\&amp;".

Examples:

====
Active search:

 $Search 192.168.1.5:412 T?T?500000?1?Gentoo$2005|
====

====
Passive search:

 $Search Hub:john F?T?0?9?TTH:TO32WPD6AQE7VA7654HEAM5GKFQGIL7F2BEKFNA|
====

==== $SR

====
 $SR _source_nick _result _free_slots/_total_slots<0x05>_hub_name (_hub_ip[:_port])[<0x05>_target_nick]|
====

Contexts: Client -> Hub -> Client, Client -> Client

Sent by a client when a match to a search is found.

If the *$Search* was a passive one, the *$SR* is returned via the hub TCP connection.
In this case, *<0x05>_target_nick* must be included on the end of the *$SR*.
The hub must strip the delimiter and *_target_nick* before sending the *$SR* to *_target_nick*.
If the search was active, it is sent to the IP address and port specified in the *$Search* via UDP.

Result is one of the following:

* _file_name<0x05>_file_size
* _directory_name

File size shall be in bytes.

"<0x05>" used above for deliminators are the 5'th character in the ASCII character set.
The brackets (<) and (>) should consequentially not be taken literally.

The port for the hub only needs to specified if its listening port is not the default 411.

On UNIX, the path delimiter (/) must be converted to (\) for compatibility.

Implementations should send a maximum of 5 search results to passive users and 10 search results to active users.

*_free_slots* are the amount of available slots left.
*_total_slots* are the total amount of slots.

For files containing TTH, the *_hub_name* parameter is replaced with "TTH:<hash>".

Active result example:

====
 $SR User1 ponies.txt<0x05>437 3/4<0x05>Testhub (192.168.1.1:412)|
 $SR User5 images 0/4<0x05>Testhub (192.168.1.1:412)|
 $SR User6 pictures 0/4<0x05>Testhub (192.168.1.1)|
====

Passive result example:

====
 $SR User1 ponies.txt<0x05>437 3/4<0x05>Testhub (192.168.1.1:412)<0x05>User2|
 $SR User5 images 0/4<0x05>Testhub (192.168.1.1:412)<0x05>User2|
 $SR User6 pictures 0/4<0x05>Testhub (192.168.1.1)<0x05>User2|
====

==== $MyINFO

====
 $MyINFO $ALL _nick _description$ $<_connection><_flag>$_email$_share_size$|
====

Contexts: Client -> Hub -> Client

This command is part of the client-hub handshake and during login, and is sent after the client receive *$Hello* with their own nick.
Client resend this on any change.
It's broadcasted to all clients.

The brackets (<) and (>) used in here should not be taken literally; they are there to visually distinguish connection from flag.
Consequently, the flag shall immediately follow the connection.

Connection is a string for the connection:

* Default NMDC1 connections types: 28.8Kbps, 33.6Kbps, 56Kbps, Satellite, ISDN, DSL, Cable, LAN(T1), LAN(T3)
* Default NMDC2 connections types: Modem, DSL, Cable, Satellite, LAN(T1), LAN(T3)
* New connections types for NMDC2: 0.005, 0.01, 0.02, 0.05, 0.1, 0.2, 0.5, 1, 2, 5, 10, 20, 50, 100, 1000

Later implementations also send other speeds.
Implementations should simply display the value to the user and not create any inhibitions based on the reported speed.

===== Flag

Flag is a ASCII character (8 bit byte).

There are multiple implementations of this byte.

The values listed here are the bits within the flag byte.
The following is the original:

[options="autowidth,header"]
|=====
|Bit |Description
|1 |Normal or no status
|2 |Away
|3 |Server status, used when the client has uptime > 2 hours, > 2 GB shared, upload > 200 MB
|4 |Fireball status, used when the client has had an upload > 100 kB/s
|=====

The values listed here are the bits within the flag byte.
Newer implementations change the numbers to be extensions of the original and are the following:

[options="autowidth,header"]
|=====
|Bit |Description
|5 |Support for TLS-encrypted client-client connections when TLS extension is supported
|6 |Support for NAT-traversal client-client connections when NAT extension is supported
|7 |Support for IPv4 when IP64 extension is supported
|8 |Support for IPv6 when IP64 extension is supported
|=====

The values listed here are decimal values.
Other implementations interpreted this to be the following:

[options="autowidth,header"]
|=====
|Decimal |Description
|1 |Normal status
|2 |Away status, used when the client has away status set
|4 |Server status, used when the client has uptime > 2 hours, > 2 GiB shared, upload > 200 MiB
|8 |Fireball status, used when the client had an upload > 100 KiB/s
|16 |TLS support, used when client supports TLS-encrypted connnections
|32 |NAT support, used when client supports NAT-traversal connnections
|64 |IPv4 support, used when client supports IPv4
|128 |IPv6 support, used when client supports IPv6
|=====

Example verification:

[options="autowidth,header"]
|=====
|Flag calculation |Result
|if Flag & 0x1 |Normal status
|if Flag & 0x2 |Away status
|if Flag & 0x4 |Server status
|if Flag & 0x8 |Fireball status
|if Flag & 0x10 |TLS support
|if Flag & 0x20 |NAT support
|if Flag & 0x40 |IPv4 support
|if Flag & 0x80 |IPv6 support
|=====

===== Tag

This addition to the *_description* field was introduced to ease concerns by hub operators that DC++ users were joining too many hubs and not allowing enough uploads.
The original DC client only allowed users to join a single hub.
The tag is now the de facto standard.

Example:

====
 <++ V:0.882,M:P,H:0/1/0,S:2>
====

* "\+\+": indicates the client (in this case DC++)
* "V": tells you the version number
* "M": tells if the user is in active "A", passive "P" or SOCKS5 "5" mode
* "H": tells how many hubs the user is on and what is his status on the hubs. The first number means a normal user, second means registered hubs and the last one operator hubs, separated by the forward slash (/).
* "S": tells the number of slots user has opened
* "O": shows the value of the "Automatically open slot if speed is below xx KiB/s" setting, if non-zero
* The brackets (<) and (>) shall be taken literally

Note that the IPv4/IPv6 extensions add additional data to the "M".
See the IPv4/IPv6 extensions for further information.

Example:

Note that the example uses "0x31" for signaling the flag as "Normal", for ease of display.

==== $Lock

====
 $Lock _lock Pk=_pk|
====

Contexts: Hub -> Client, Client -> Client

This is a mechanism to request "certification" for verification.
The lock is a command that added by NMDC to keep other clients (such as DC++) from being able to use NMDC hubs.
The lock require a response (given in a *$Key*) that needs to be calculated, as per the lock's data.
Hubs are not required to check the validity of the response, but must still send it.

Note this command, and its use, are used for all connections.

This command should be the first to be sent in a client to hub connection.
This command should be sent after both have used *$MyNick* in a client to client connection.
Both clients (in a client to client connection) should send *$Lock*.

The lock data is a sequence of random characters, excluding space ( ), dollar sign ($) and a pipe (|).

*Pk* was originally intended for use with SSL/TLS keys for secure connections, but is not used by any implementation today.
Some implementations send their name and version in this field.

Implementation note: In NMDC hub;

* Lock's length varied from 46 to 115 characters
* Pk's length was static with 16 characters
* Lock's characters varied from ASCII code point 37 to ASCII code point 122

Examples:

See *$Supports* for the use of "EXTENDED".

====
 $Lock EXTENDEDPROTOCOLABCABCABCABCABCABC Pk=DCPLUSPLUS0.882|
 $Lock EXTENDEDPROTOCOL_NMDC_TLS_2903 Pk=Verlihub 1.5.0.0|
====

==== $Key

====
 $Key _key|
====

Contexts: Client -> Hub, Client -> Client

The key is given as a response for a *$Lock* command, as calculated by the following algorithm.

The key has exactly as many characters as the lock.
Except for the first, each key character is computed from the corresponding lock character and the one before it.
If the first character has index 0 and the lock has a length of len then:

====
 for (i = 1; i < len; i++) { key[i] = lock[i] xor lock[i-1]; }
====

The first key character is calculated from the first lock character and the last two lock characters:

====
 key[0] = lock[0] xor lock[len-1] xor lock[len-2] xor 5
====

Next, every character in the key must be nibble-swapped:

====
 for (i = 0; i < len; i++) { key[i] = ((key[i] << 4) & 240) | ((key[i] >> 4) & 15); }
====

Finally, the characters with the decimal ASCII values of "0", "5", "36", "96", "124" and "126" cannot be sent to the server.
Each character with this value must be substituted with the string "/%DCN000%/", "/%DCN005%/", "/%DCN036%/", "/%DCN096%/", "/%DCN124%/" and "/%DCN126%/" respectively.
The resulting string is the key to be sent to the server.

If your programming language of choice doesn't have "xor" or "shift" operations on characters, convert them to integers.
If it doesn't have a bit "shift" at all, then "x << y = x*(2y) and x >> y = x/(2y)" for all integers x and y (** is the exponent operation or "to the power of").
Be sure to use unsigned values everywhere and do not do sign extension.
Shift operations always lose the high or low bit (they are not roll operations).
The (&) - and, and (|) - or operations are all logical, not boolean (eg. 6 & 13 = 4, not 1).

When the hub connects to the hublist, it must undergo a similar *$Lock*/*$Key* negotiation.
The *_key* calculation is the same, but the special number "5" in the second step is replaced with the following value is not computed from the hub's listening port, but rather the random outgoing port that the socket selects.

Note that the data sent should be in its raw form.

Example:

Note that this (and every other) example uses "011010110110010101111001" as key, but it should be interpreted as a binary value.

====
 $Key 011010110110010101111001|
====

==== $IN

====
 $IN _nick$_data[$_data]|
====

Contexts: Client -> Hub, Hub -> Client

This command is designed to replace the static *$MyINFO*.
This command consist of separate smaller parts which all have a 1-byte identifier and are separated by a dollar sign ($).

If a client wishes to remove a part of its *$IN* (say for example its description), it must send this parts identifier immediatly followed by the dollar sign ($), indicating it is empty.

The order in which parts are sent is free to choose, but tag parts should be grouped together.

Add *IN* to the *$Supports* to indicate support for this.

This command deprecates *$OpList* and *$BotList*.

A client tag has only one identifier indicating it is concerning the tag, but all parts of this tag also have their own 1-byte identifier.
In the tag, the parts are delimited with a space ( ).

The data consist of two elements: identifier and its data.

The following table lists the identifiers:

[options="autowidth,header"]
|=====
|Identifier (character code) |Description
|D (68) |Description
|T (84) |Tag
|C (67) |Connection
|F (70) |Status flag
|E (69) |E-mail address
|S (83) |Share size in bytes
|=====

Examples:

====
 $IN john$Dmy_new_description|
 $IN john$S1024|
 $IN john$S1024$$Dmy_new_description|
====

The tag has the following identifiers in the data:

[options="autowidth,header"]
|=====
|Identifier (character code) |Description
|c (99) |Client
|v (118) |Version
|m (109) |Mode
|h (104) |Hub count, "x/y/z" - where "x" is the number of hubs as a normal user, "y" as the number of hubs as registered and "z" as the number of hubs as operator
|s (115) |Slots
|f (102) |Free slots
|l (108) |Bandwidth limit, "L:" and "B:" in $MyINFO
|o (111) |"O:" in $MyINFO
|r (114) |"R:" in $MyINFO
|=====

Tag identifiers are separated by a space ( ).

Examples:

====
 $IN john$Ts3|
 $IN john$Tdc++ v0.882|
====

The status is a 32-bit integers where the bits are according to the following table:

[options="autowidth,header"]
|=====
|Bit |Description
|1 |Default value
|2 |User is away
|3 |User is server
|4 |User is fireball
|5 |User is OP
|6 |Client is a bot
|7 |Client is in DND mode
|8 |Client support encryption
|9 |Client supports partial search
|=====

Bit 5 and Bit 6 of the 32-bit status flag are used to indicate whether a user is an OP or whether the *$IN* string send by the hubsoft belongs to a bot.
These values are read-only and should never be changed by a client.
The hubsoft must disconnect for this.
If a client connects and has successfully logged in with the correct password, the hubsoft will set bit 5 of the status flag and sends this part to all connected users, including the newly connected OP.
The connecting client must save the status flag it received from the hub and use it when updating status such as away and fireball.
However, as said, it is not allowed to set or reset bit 5 and bit 6 of the status flag.

Bit 7 of the 32-bit status flag indicates if the client is in DND-mode (Do-Not-Disturb).
Unlike "Away" mode, this mode will prevent the client to receive any PMs.
Clients are responsible themselves for setting/resetting this bit.
Once this bit is set, and the hub receives a *$To:* string for a client in DND-mode, the hub must ignore the *$To:* and reply to the sender with a message that the receiver is in DND-Mode.
A client having this bit set, should automatically reset this bit when sending a pm itself.
Ideally, newer clients supporting *IN*, may prevent themselves from sending *$To:* strings to other clients having this bit set.
The hub will always have the last the say in forwarding a PM or not.
*$To:* strings generated by the hubsoft to the client are not included in this and will be sent regardlessly of status (i.e. messages from bots).

==== FeaturedNetworks

*$FeaturedNetworks* is a protocol extension of the APN MultiHubChatsystem to identify the different hubs and other entry points (IRC, Telnet) etc.
It was primarily created to aid APN developers and to allow a better integration of multi hub chat systems.

Messages coming through the chat network are prefixed with an unique network node (entry point) identifier, normally three characters long.
The central point of the chat network is a single hub that collects chat messages from one entry point and sends them back all other entry points.

Add *FeaturedNetworks* to the *$Supports* to indicate support for this.

Syntax:

An APN MultiHubChat message normally has this format:

"<(YYY)XXXXX> MMMMMMM|" - where "YYY" is the entry point prefix, "XXXXX" is the username and "MMMMMMM" is the message.

To allow the different entry point handlers to identify which messages are coming from other multi hub chat entry points, there is a command send by the hub after login called *$FeaturedNetworks*:

"$FeaturedNetworks YYY+++$$+++YYY$YYY+++$$+++|" - "YYY" stands for one entry point to the chat network.
In the biggest currently running instance of the APN MultiHubChat system, five or more different prefixes are used.

===== Implementation

If implemented, this command could be sent from one of the entry point hubs aswell to aid the client in distinguishing user set prefixes ([BBB], [psv], (FUG) etc..) from network prefixes, and can be used by bots to detect prefix abuse.

The prefixes are to be defined by the network administrator.
In the biggest running instance of the network however, the following prefixes are used by several MHC plugins for the different entry points:

* APx - Hub x (DC, where x is Â¹,Â³ or Â²)
* APt - Telnet Access (Telnet Chat Plugin)
* IRC - IRC Access (IRC plugin)
* APs - Shoutcast (Shoutcast Announcer Plugin)

*$FeaturedNetworks* can be implemented by virtually any hub by either using the MHC bot or by injecting it into the server/client stream using a textfile (like a MOTD).

==== $GetZBlock

====
 $GetZBlock _start _bytes _file_name|
====

*_start* is the 0-based (yes, 0-based, not like get that's 1-based) starting index of the file used.

*_bytes* is the number of bytes to send.

*_file_name* is the filename.

The other client then responds "$Sending <bytes>|<compressed data>", if the sending is ok or "$Failed <errordescription>|" if it isn't.

If everything's OK, the data is sent until the whole uncompressed length has been sent.
*_bytes* specifies how many uncompressed bytes will be sent, not compressed, as the sending client doesn't know how well the file will compress.
*$Sending* is needed to be able to distinguish the failure command from file data.
Only one roundtrip is done for each block though, minimizing the need for maintaining states.

Compression: Compression is done using ZLib (v1.1.4 in DC++ 0.21's case), using dynamic compression level.
The compression level can of course be changed by the implementator to reduce CPU usage, or even just store compression in the case of non-compressible files, which then works as adler32 check of the transferred data.

Support of *$GetZBlock* also implies support for *$UGetZBlock*.

==== $UGetBlock

====
 $UGetBlock _start _bytes _file_name|
====

This is the same command as *$GetZBlock* except this command is uncompressed and the filename is UTF-8 encoded.

The filename is encoded as UTF-8, which allows filenames to use characters that are not in the system's encoding.
*$UGetBlock* must be implemented if *XmlBZList* is advertised.

==== $UGetZBlock

This is the same as *$UGetBlock* except that the stream is compressed using ZLib.

==== $GetTestZBlock

This command is deprecated and was a test command during the development of *$GetZBlock*.
Implementations should not use this command.

Diff is the difference between the end byte and start byte.
If the requested bytes was *-1* then diff should be omitted.

This is sent as a response to *$GetZBlock*, *$UGetBlock* and *$UGetZBlock*.

The start and end byte are 0-based; the first byte of a file is assumed to be the byte number *0*.

|0 |Separator
|1 |Raw
|2 |Raw nick limited (same as raw with the exception that it should only be used once per %[nick])
|255 |Erase all previously sent commands
|=====

*_context* is a integer that controls which contexts the menus will be shown.
The value is derived by logical OR of the following values:

[options="autowidth,header"]
|=====
|Value |Description
|1 |Hub context
|2 |User context
|4 |Search context
|8 |File list
|=====

*_details* differ depending on the type;

[options="autowidth,header"]
|=====
|Type |Detail information
|0 and 255 |Leave this field empty
|1 and 2 |Detail should be "_title$_command".
|=====

===== Escaping

Escaping of dollar and pipe is necessary for the *_command* in 'raw' mode.
The DC++ escape sequence will be used.
I.e. "\&#124;" for pipe, "\&#36;" for dollar and "\&amp;" for the ampersand.
Escaping is used for all fields before they are sent to the hub / shown to the user.
As with all NMDC commands, they must be terminated by the pipe character.

===== Details: Separator

====
 $UserCommand 0 _context|
====

Will add a menu separator (vertical bar) to the specified contexts.
It is legal to add text (after the space) before the pipe, but it won't be used (yet).

===== Details: Raw

====
 $UserCommand 1 _context _title$_raw|
====

Will add a raw menu item with title *_title* with command *_raw*.
This command must end with a "\&#124;", if not it should be discarded.
The raw command may be used to specify multiple commands to be sent to the hub.

===== Details: Raw nick limited

====
 $UserCommand 2 _context _title$_raw|
====

Is exactly the same as _raw_, except that the command should only be run once per "%[nick]".
This is to prevent the client from sending out more than one message that disconnects someone.
Generally, this is only useful in the User-File context (e.g. viewing search results) where it is possible to select one user multiple times.

===== Details: Erase

====
 $UserCommand 255 _context|
====

Will erase all commands that the hub has sent previously.
This is for hubs/scripts that allow for updates while running.
The erase all is intentional, keeping it simple.
Note that contexts must still be used, and that erasing will remove all commands that match any of those ORed contexts (i.e. 7 will remove commands previously sent with any context of 1 through 7) but only from that context.

Examples:

====
 $UserCommand 2 6 Kick$&#36;To: %[nick] From: %[mynick] &#36;<%[mynick]> You are being kicked====|&#36;Kick %[nick]&#124;|
 $UserCommand 255 1|
====


=== Extensions (features)


==== NoHello

Contexts: Client -> Hub

This indicates that the client doesn't need either *$Hello* or *$NickList* to be sent to it when connecting to a hub.
To populate its user list, a *$MyINFO* for each user is enough.
*$Hello* is still accepted, for adding bots to the user list.
DC++ still sends a *$GetNickList* to indicate that it is interested in the user list.
During login, hubs must still send *$Hello* after *$ValidateNick* to indicate that the nick was accepted.

Add *NoHello* to the *$Supports* to indicate support for this.


==== ChatOnly

Contexts: Client -> Hub

This indicates that the client only support chat capabilities to allow the client to bypass hub rules (that relate to file sharing).
The client should be disconnected if it sends *$Search*, *$SR*, *$SA*, *$SP*, *$ConnectToMe* or *$RevConnectToMe*.

Add *ChatOnly* to the *$Supports* to indicate support for this.

Hubs known to support this extension: Verlihub, FearHub


==== TTHSearch

Contexts: Client -> Hub -> Client

This indicates that the client support searching for queued files by TTH.
See *$Search* for details.

Add *TTHSearch* to the *$Supports* to indicate support for this.


==== XmlBZList

Contexts: Client -> Client

Usage: Supporing this means supporting UTF-8 XML file lists with the following general structure.

====
 <FileList Version="1" Generator="dc client name and version">
  <Directory Name="xxx">
   <Directory Name="yyy">
    <File Name="zzz" Size="1"/>
   </Directory>
  </Directory>
 </FileList>
====

In each directory, including the root, the name of the entity must be case-insensitive unique in that level of the hierarchy.

Other fields may be added as necessary.
DC++ for instance adds the TTH attribute to each file it knows the TTH root of in Base32 encoding.

The file list is available as "files.xml.bz2" (vs MyList.DcLst), and is compressed using BZip2.

To retrieve unicode files from the file list, the client may also support the above *GetZBlock* and its UTF-8 derivatives.
Support for *XmlBZList* implies support for *$UGetBlock*, so files are guaranteed to be retrievable.

*$UGetBlock* follows *$UGetZBlock* semantics, but without compressing the data.
The *_bytes* parameter of *$Sending* specifies how many bytes will be sent.

Don't touch version.
Add your own, with a different name, if you feel compelled.

Don't trust generator to determine features of the file list.
It's there mainly for debugging and informative purposes.

Add *XmlBZList* to the *$Supports* to indicate support for this.

DC\++ supported the feature *XmlBZList* and the commands *$GetBlock*, *$UGetBlock* and *$UGetZBlock* in versions 0.307 to 0.695.
DC\++ dropped support for the commands in version 0.696, whilst not removing the feature announcement.
I.e., DC++ signals in the *$Supports XmlBZList* while it does not support the actual commands.


==== Minislots

Contexts: Client -> Client

ToDo: *Minislots* vs *MiniSlots* - help needed.

This allows the other client to use a free slot for small files / file list.

*$Supports* is needed because the Neo-Modus DC client closes the file list browser when the connection is broken, which it becomes when the client on the other side tries to download its first file and fails because it has no real slot.

Add *Minislots* to the *$Supports* to indicate support for this.


==== TTHL

Contexts: Client -> Client

Supporting this means supporting the upload of TTH leaf data.
Instead of transfering the file itself, the TTH data of all leaves is transferred in binary.
The size transferred back is the number of bytes of leaf data, from this and the file size the receiving client can calculate which level (tree depth) the sending client is offering.
The receiver should obviosly check that the received leaf data is correct by rebuilding the tree and checking that it's recorded root matches.

Add *TTHL* to the *$Supports* to indicate support for this.


==== TTHF

Contexts: Client -> Client

Supporting this means supporting file identification by TTH root.
This means supporting downloads by TTH root instead of share directory and name.
The advantage is that moved files can still be found by the downloader without requeuing the file.

The extension adds a namespace "TTH" before the ADC file root.
A TTHF filename has the following syntax: TTH/<TTH root in base32, 192 binary bits>

Ie the TTH namespace consists of TTH root values directly under the "TTH/" root.

The naming scheme is valid in all types (ie also for getting TTH leaves).

Add *TTHF* to the *$Supports* to indicate support for this.


==== TTHS

Contexts: Client -> Hub -> Client

State: Connected

====
 $Supports TTHS|
 $SA _hash _addr:_port|
 $SP _hash _nick|
====

*TTHS* stands for "TTH short", and relies on *TTHSearch* extension due to TTH relation.
A client can not support this extension without supporting *TTHSearch*.

Add *TTHS* to the *$Supports* to indicate support for this.

Clients who support this, send short command to the hub that supports it.
The hub forwards short command to other clients who support it.
The hub converts short command to old fashion search request and sends it to other clients who don't support short command.

Clients who don't support this, send old fashion search request to the hub.
The hub forwards old fashion command to other clients who don't support short command.
The hub converts old fashion search request to short command and sends it to other clients who support it.

Example active search request:

====
 (new command)
 $SA LWPNACQDBZRYXW3VHJVCJ64QBZNGHOHHHZWCLNQ 192.168.1.2:412|
 (old command)
 $Search 192.168.1.2:412 F?F?0?9?TTH:LWPNACQDBZRYXW3VHJVCJ64QBZNGHOHHHZWCLNQ|
 (60 vs 76 bytes)
====

Example passive search request:

====
 (new command)
 $SP LWPNACQDBZRYXW3VHJVCJ64QBZNGHOHHHZWCLNQ john|
 (old command)
 $Search Hub:john F?F?0?9?TTH:LWPNACQDBZRYXW3VHJVCJ64QBZNGHOHHHZWCLNQ|
 (49 vs 69 bytes)
====

Meaning of this extension is to save some server upload bandwidth by shortening down the most frequently used search command - looking for download alternatives using TTH.
Here are some statistics regarding these commands comparing to old fashion commands:

====
 [*] $Search: 344579
 [*] $Search Hub: 379696
 [*] $SA: 243379
 [*] $SP: 292746

 [*] Total upload: 127.32 GB [395.34 KB/s]
 [*] Upload saved with ZLib: 44.52 GB
 [*] Upload saved with TTHS: 6.29 GB
====

Note: This extension does not implement file size restriction and applies only to TTH searches.

Hubs known to support this extension: Verlihub, FearHub

Clients known to support this extension: FearDC


==== ZLIG

Supporting this means that ZLib compressed *$ADCGET* transfers are supported.

Add *ZLIG* to the *$Supports* to indicate support for this.


==== ACTM

Contexts: Client -> Hub -> Client

====
 $CTM _nick$_port$_id|
 $CTM _addr$_port$_id|
 $RCTM _nick|
 $CTM _id|
 $Error Invalid ID|
====

AdvancedConnectToMe (ACTM) is a replacement for the *$ConnectToMe* and *$RevConnectToMe* commands.

Add *ACTM* to the *$Supports* to indicate support for this.

Implementations supporting *ACTM* must reply to incoming *$ConnectToMe* and *$RevConnectToMe* requests, but will themselves always send *$CTM* or *$RCTM*.

During requests, the clients send a 4-digit hexadecimal ID.
This ID is an incremental number that is given out for each *$CTM* that it sent.
When a connection between two clients is established, the other party must echo back this 4-digit ID.
This is done after *$Supports* but before *$Direction*.
If the 4-digit ID is not any of the unhandled IDs given out by the requesting client, it must signal *$Error* and disconnect.

Example handshake:

[options="autowidth, header"]
|=====
|Client (john, passive)|Server (peter, active)|Hub

|$RCTM peter\| | |
| | |$RCTM john\|
| |$CTM john$413$A91E\| |
| | |$CTM 192.168.1.4$413$A91E\|
|connect(192.168.1.4, 413) | |
| |$MyNick peter\| |
|$MyNick john\| | |
|$Lock EXTENDEDPROTOCOL Pk=DCPLUSPLUS0.880\| | |
| |$Lock EXTENDEDPROTOCOL Pk=DCPLUSPLUS0.882\| |
|$Supports ACTM\| | |
|$CTM A91E\| | |
|$Direction Download 17762\| | |
|$Key 011010110110010101111001\| | |
| |$Supports ACTM\| |
| |$Direction Upload 6494\| |
| |$Key 011010110110010101111001\| |
|$Get files.xml.bz2$0\| | |
| |$Send\| |
|=====

Notes:

* "connect()" is not literal
* "EXTENDEDPROTOCOL" has been shortened for better visibility
* There is no known implementation of *TLS* or *NAT* with this extension

==== SaltPass

Contexts: Client -> Hub -> Client

====
 $GetPass _encoded_data|
 $MyPass _encoded_data|
====

This feature offers passwords to be salted and hashed, which means that passwords are no longer sent in plaintext.
This adds "random data" to the *$GetPass* command.

The random data should be Base32 encoded.

The data that is sent back in the *$MyPass* shall be the password followed by the random *_encoded_data*, passed through the https://en.wikipedia.org/wiki/Tiger+++_+++(hash_function)[Tiger192] algorithm and then encoded with Base32:

====
 base32_encode(tiger_hash(_password + _decoded_data))
====

Add *SaltPass* to the *$Supports* to indicate support for this.

The algorithm here is a port from ADC https://dc-protocols.github.io/ADC.html#_gpa[GPA] and https://dc-protocols.github.io/ADC.html#_pas[PAS].

Example:

[options="autowidth,header"]
|=====
|Client|Hub
|$Supports SaltPass\| |
|$ValidateNick john\| |
| |$Supports SaltPass\|
| |$GetPass ABC234\|
|$MyPass DEF567\| |
| |$Hello john\|
|=====

Hubs known to support this extension: FearHub

Clients known to support this extension: BDC++, FearDC


==== IPv4

Contexts: Client -> Hub -> Client

This feature is used to indicate IPv4 support when a client is connecting from a IPv6 address.

The hub should send a *$ConnectToMe* to the client, to indicate a download from the hub.
The client will connect to the hub address and port as in a normal client to client connection, this time using the client's IPv4 address.
The hub should disconnect after it has received the *$MyNick* command.

The hub should later verify in connection attempts with other IPv4 clients that the IPv4 address matches.

Once the hub has received an IPv4 connection and gathered the IPv4 address, it should set the IPv4 bit in the *$MyINFO* command.

Add *IPv4* to the *$Supports* to indicate support for this.

==== IPv6

Contexts: Client -> Hub -> Client

This feature is used to indicate IPv6 support.

IPv6 addresses are specified in https://datatracker.ietf.org/doc/html/rfc4291[RFC 4291] format.

If the client has an IPv4 connection, it should also signal the use of IPv4.
Clients should use the same TCP and UDP ports for both IPv4 and IPv6 if both are supported.
The connection mode (passive, active, SOCKS5) can be different.

The hub is required to set the IPv6 bit in the *$MyINFO* command.

The connection mode in the *$MyINFO* tag changes from "M:X" where "X" is the connection mode ("A" - active, "P" - passive, "5" - SOCKS5) to "M:XY" where "X" is the connection mode of IPv4 and "Y" is the connection mode of IPv6.
If a client does not support IPv4 or the IPv4 check failed, the first character will be "N" for not supported.

Add *IP64* to the *$Supports* to indicate support for this.

A client that support IPv4 and IPv6 will only use one form when sending messages to a hub.
The hub is responsible for translating the command into the correct IPv4/IPv6 address.
E.g., if a *$Search* is sent with a IPv6 address, the hub will send the client's IPv4 address to those who only support IPv4.
This minimizes the amount of traffic toward the hub.
If a client sent a passive search request, then it is only sent to active users supporting the same TCP/IP protocol.
This is regardless if the client is active in the other protocol.
I.e., if a passive search request is sent with a IPv4 address, that search request will only be forwarded to IPv4 users and not converted to an IPv6 request, regardless if the client is active in IPv6.


==== TLS

Contexts: Client -> Hub -> Client

This feature is used to indicate support for https://en.wikipedia.org/wiki/Transport_Layer_Security[TLS-encrypted] client-client connections.
This feature can be used in conjunction with *NAT* feature specified below.

Implementations shall add an "S" to the TLS port in a *$ConnectToMe*.

Add *TLS* to the *$Supports* to indicate support for this.

Example connection request:

====
 $ConnectToMe john 192.168.0.1:412S|
====

Hubs known to support this extension: Verlihub, FearHub

Clients known to support this extension: FearDC


==== NAT

Contexts: Client -> Hub -> Client

This feature is used to indicate support for https://en.wikipedia.org/wiki/NAT_traversal[NAT-traversal] in passive client-client connections.
This feature can be used in conjunction with *TLS* feature specified above.

Implementations shall add a "N <nick>" and "R" to the port in a *$ConnectToMe*.

There is no known *$Supports* flag for this feature, but logic says that *TLS* flag implements this variant as they can be used together.

Example connection request:

====
 $RevConnectToMe john peter|
 $ConnectToMe john 192.168.1.3:412N peter|
 $ConnectToMe peter 192.168.1.3:412R|
====

Hubs known to support this extension: Verlihub, FearHub

Clients known to support this extension: FearDC


==== NATIP6

Contexts: Client -> Hub -> Client, Client -> Hub

This feature is used to connect two passive users over IPv6, also when the hub connection itself uses IPv4.
It works like the *NAT* feature specified above, with the addition that the hub proves the IPv6 address of each user before giving it to others.
It is different from the *IP64* extension: a client built for one can not use the other.

Add *NATIP6* and *TLS* to the *$Supports* to indicate support for this.
The hub adds *NATIP6* to its *$Supports* only when client stated both flags and the hub can accept connections over IPv6.
A client shall ignore every address in brackets from a hub that did not state this flag.

After login the hub asks the client to prove its address, with the IPv6 address and port of the hub and a one time token:

====
 $ConnectToMe peter [2001:db8::1]:411 0123456789abcdef0123456789abcdef|
====

The client connects there over IPv6 and sends only the token, nick is not needed:

====
 $MyNick 0123456789abcdef0123456789abcdef|
====

The hub remembers the source address of this connection for this user and closes the connection.
The token works once, for 60 seconds.
A source address of a completed TCP connection is used because an address stated by a client could point to anyone.

When both users have proved their addresses, the hub forwards every *NS* and *RS* request of the *NAT* feature in two forms, IPv6 first, and adds the sender to *RS*.
The port of the IPv6 form is the port client stated:

====
 $RevConnectToMe john peter|
 $ConnectToMe john 192.168.1.3:412NS peter|
 $ConnectToMe john [2001:db8::2]:412NS peter|
 $ConnectToMe john 203.0.113.2:6000NS peter|
 $ConnectToMe peter 192.168.1.4:413RS|
 $ConnectToMe peter [2001:db8::3]:413RS john|
 $ConnectToMe peter 203.0.113.3:7000RS john|
====

Clients answer one *RS* for both forms.
Each client connects to the other one from the address it proved, which matters on computers with several IPv6 addresses, because a firewall lets through only the address that was dialed.
Connections over IPv6 shall use TLS 1.3 or newer, there is no form without *S*.
The hub can not see these connections, so each client enforces this by itself.
The first connection that succeeds is used and the other one is dropped, a client may wait some seconds with IPv4 for this.

Hubs known to support this extension: Verlihub

Clients known to support this extension: FearDC


==== PortTest

Contexts: Client -> Hub -> Client

This feature is used by a client to find out if its ports can be reached from outside, and how others see its address.
Many hubs do not send *$UserIP* to users, so this does not depend on it.

Add *PortTest* to the *$Supports* to indicate support for this.
The hub adds it to its own *$Supports* when client stated it, and shall disconnect a client that sends the command without stating the flag.

The client sends its TCP, TLS and UDP port:

====
 $PortTest 412 413 414|
====

The hub answers with the address it sees, tries to connect to both TCP ports, sends a UDP packet to the UDP port and tells the result:

====
 $PortTest ip 203.0.113.2|
 $PortTest 412 ok|
 $PortTest 413 fail|
 $PortTest 414 udp 0123456789abcdef0123456789abcdef|
====

The UDP packet contains the same token, so the client itself sees if it arrived:

====
 $PortTest 0123456789abcdef0123456789abcdef|
====

When the hub has too many tests running, or this connection had a test less than a minute ago, it answers:

====
 $PortTest busy|
====

The client keeps the result it had and can ask again later, a minute after its last test.
The hub connects only to the address of the user who asked, closes each connection without sending anything, and runs at most one test per minute for one connection.
A client that gets everything through can use active mode on this hub, otherwise passive mode on this hub.

Hubs known to support this extension: Verlihub

Clients known to support this extension: FearDC


==== FDCX

Contexts: Client -> Hub -> Client, Client -> Client

This feature is used to tell other users the address of a FDCX wallet, so they can send coins to it, for example a tip.
Only users who state the flag get addresses, other clients never see them.

Add *FDCX* to the *$Supports* to indicate support for this.
A client states the flag only when it shares an address itself and has a certificate for TLS, a client without them does not use this feature at all.
The hub adds it to its own *$Supports* when client stated it and the hub has this feature turned on, otherwise the command from that client is unknown to the hub.
A client shall not send the command to a hub that did not state the flag, and shall ignore it from such a hub.

The client sends its address with the keyprint of its own certificate, also again when one of them changes, or nothing to remove the address when it stops sharing during the login:

====
 $FDCX fdcx1qqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqq98qp4q SHA256/AJVNTMKKORJ3OSENVIGGVS6CLCYVA32SYRA4PRDFI5GBUVSDST7Q|
 $FDCX |
====

The address is a bech32 or bech32m address with prefix *fdcx1* on mainnet, *tfdcx1* on testnet or *rfdcx1* on regtest, at most 90 characters, sent in lower case.
The keyprint is *SHA256/* and the Base32 of the SHA-256 digest of the DER certificate the client uses for TLS on client to client connections, 52 characters without padding, in upper case.
An address always comes with its keyprint.
The hub checks the checksum and the form of the keyprint and disconnects a client that sends anything else.
The client can send it before its login ends, the hub keeps it and passes it on when user is in the list.

The hub adds the nick of the sender itself, so nobody can send an address for another user, and sends it to every user with this flag, the sender too.
No address after the nick means the user removed it:

====
 $FDCX peter fdcx1qqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqq98qp4q SHA256/AJVNTMKKORJ3OSENVIGGVS6CLCYVA32SYRA4PRDFI5GBUVSDST7Q|
 $FDCX peter|
====

After login the hub sends the addresses of all other users that have one in one command, each entry ends with *$$*, like the *$UserIP* list:

====
 $FDCX peter fdcx1qqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqq98qp4q SHA256/AJVNTMKKORJ3OSENVIGGVS6CLCYVA32SYRA4PRDFI5GBUVSDST7Q$$john fdcx1qqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqq98qp4q SHA256/S3MWGLZWGVSMYMBSKIKATTZCVBJPEAZO5QEZ5VMWPQGQADHMMB5A$$|
====

A client accepts both forms from the hub, one user with or without *$$* at the end, and a list.
The command can come before *$MyINFO* of that nick, so a client keeps it until the user is known.
A client uses only addresses of the network it uses itself, ignores an address without valid keyprint, and should show the whole address before sending coins.
A hub may limit how often a user sends the command.

A hub can have an address of its own, so users can send coins to the hub itself, for example a tip.
It sends its address after login, and again to every user with this flag when it changes, with the smallest tip in whole coins that it thanks for in main chat, *0* when it thanks for none.
Nothing after the command name means the hub has no address any more, a hub without an address sends nothing at login:

====
 $FDCXH fdcx1qqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqq98qp4q 5|
 $FDCXH |
====

A client uses the address only when it is of the network the client uses itself.
The hub sends the address on its own connection, so a client trusts it as much as that connection: through a proxy without TLS or without a checked hub certificate it can be changed on the way, and a client should warn its user before coins are sent.

When a payment to the address of the hub went out and is at least the amount the hub named, the client of the payer can send its transaction id, 64 lower case hex characters, once for each payment:

====
 $FDCXT 0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef|
====

The payment names its payer in the data of an OP_RETURN output: *feardc:* and the first 16 bytes of the SHA-256 digest over the hub name, a zero byte and the nick of the payer.
The hub name is the part of *$HubName* in its first 1024 bytes before the first space, dash and space, where the topic starts, and both name and nick are the bytes the hub sends, so the encoding of a client plays no part.
Only the payer can put this data into the payment, so nobody can claim the payment of another user.

The hub checks the payment itself, for example with an FDCX explorer, and asks again while it is not in a block yet.
It thanks in main chat only for a confirmed payment that pays at least the named amount to the address of the hub, names the nick that sent the command, and is not older than an hour, each payment once.
Otherwise it tells the payer why the tip is not announced.
A hub that did not state the flag treats the command as unknown, like *$FDCX*, and may limit how often a user sends it.

Between clients the flag is in *$Supports* of the client to client handshake, so a client can check the address the hub passed on with the client of that user itself.
A client states the flag there only when it shares an address, on connections that belong to a hub with this feature.
When both clients state the flag and the connection uses TLS, each client sends its address after *$Key*, without keyprint, its certificate on that connection shows it, also on connections for files:

====
 $FDCX fdcx1qqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqq98qp4q|
====

The address is sent only once per connection, never empty, and never over a connection without TLS.
A client ignores the command when it did not state the flag itself, and treats an empty or invalid address as no answer.
To check an address before paying, a client asks for a connection in the usual way, with *$ConnectToMe* or *$RevConnectToMe*, states *Download* in *$Direction* and closes the connection when the address arrived, the other client needs no free slot for it.
When the address of the client differs from the one the hub passed on, or no connection is possible, the client should warn its user before coins are sent.
When the other client shows a certificate with another keyprint than the one the hub passed on with its address, somebody stands between the two clients, so the address is not confirmed and the client shall warn its user.
The keyprint protects against anyone between the two clients, not against the hub that passes both on.
When the connection to the hub itself can be changed on the way, for example a connection through a proxy without TLS or without a checked hub certificate, address and keyprint can be changed together, so a client should warn its user before coins go to a client it has not seen before.

When two clients can not connect to each other, for example both are passive, they meet at the FDCX relay instead.
The client that checks makes a random token of 32 lowercase hex characters and sends it to the other user through the hub, the hub adds the nick of the sender and passes it on only to a user with this flag:

====
 $FDCXR peter 0123456789abcdef0123456789abcdef|
 $FDCXR john 0123456789abcdef0123456789abcdef|
====

The first line goes from client to hub, the second from hub to *peter*, when *john* sent it.
The hub drops the command when the user is not online or did not state the flag, and the checking client gives up on its own time.
A hub that did not state the flag treats the command as unknown, like *$FDCX*, and may limit how often a user sends it.

Both clients connect to the relay with TLS and send the token, the relay answers both with an empty command when the second one came, then passes everything between them:

====
 $FDCXR 0123456789abcdef0123456789abcdef|
 $FDCXR|
====

After that both run the usual client to client handshake, the client that checks starts it like after *$ConnectToMe* and states *Download*, then each sends its address with *$FDCX*.
TLS ends at the relay, so there each client also sends its own client certificate and a signature, both in base64 on one line:

====
 $FDCX fdcx1qqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqq98qp4q MIIDBjCCAe6gAwIBAgIB... kq3ZpG8x...|
====

The certificate is the DER form of the certificate the client uses for TLS on direct connections.
The signature is SHA-256 with the key of that certificate over the bytes *FDCX relay|<token>|<own nick>|<address>*, with the relay token, the nick of the sending client on that hub in the encoding of that hub, as it goes in $MyNick, and the address it sends.
The other client checks the signature with that certificate and the nick it knows for this user, an answer without good signature is no answer.
Its keyprint, SHA-256 of the DER certificate, is the same one a direct connection shows, so a client compares it with the one the hub passed on and the one it saw for this user before.
The relay passes only a few kilobytes and closes the connection after a short time, a client never sends or asks for files there.
The relay stores nothing, the client checks the keyprint of the relay certificate before it sends anything.

Hubs known to support this extension: Verlihub

Clients known to support this extension: FearDC


==== CCPM

Contexts: Client -> Hub -> Client, Client -> Client

This feature is used for private chat directly between two clients, like the *CCPM* extension of ADC.
Messages do not go through the hub, the hub only allows or refuses each channel, by the same rules as private messages through the hub.
Channels go only over TLS.

Add *CCPM* and *TLS* to the *$Supports* to indicate support for this.
The hub adds *CCPM* to its own *$Supports* only when client stated both flags and the hub has this feature turned on.
A client shall not use the forms below on a hub that did not state the flag, and shall ignore them from such a hub.

The client asks for a channel with a *P* right before the *S* of the port in *$ConnectToMe*, or with the word *P* after the nick in *$RevConnectToMe*, there is no form without *S*:

====
 $ConnectToMe john 192.168.1.3:412PS|
 $RevConnectToMe peter john P|
====

Two passive users use the forms of the *NAT* feature, with *P* in the same place:

====
 $RevConnectToMe peter john P|
 $ConnectToMe peter 192.168.1.4:413NPS john|
 $ConnectToMe john 192.168.1.3:412RPS|
====

The hub adds the nick of the sender to every form with *P* it passes on, when the form has none, so the other client knows who asked:

====
 $ConnectToMe john 192.168.1.3:412PS peter|
 $ConnectToMe peter 192.168.1.4:413RPS john|
====

Before the hub passes a request on, it checks that the other user stated the flag, that TLS of both users fits, that both users may use private chat with each other and that both users can reach each other.
Rules for downloads, like minimum share, class to download, hidden share or chat only mode, are not for these requests.
The hub never passes a form with *P* to a user who did not state the flag.
The hub disconnects with a message a client that sends a form with *P* without the agreed flag, or a malformed form.
When the hub refuses, it tells the sender why:

====
 $CCPM john off|
 $CCPM john unreachable|
 $CCPM john denied|
====

*off* means the hub turned the feature off, or the other user is offline, a bot or the sender itself, or has no *CCPM* or no fitting TLS, *unreachable* means both users are passive without *NAT* of both or the hub keeps them apart, *denied* means one of both users may not use private chat with the other or the hub refused the channel for another reason.
The client then sends its private messages through the hub with *$To*.
A client asks for a channel only when its user chooses a direct private chat with that user, and sends no private messages to that user through the hub while it waits.
When the channel does not come up within some seconds, the client also falls back to the hub.

The client that connects got the request with *P*, so it knows the purpose of the connection, and it is the one that sends *$Supports*, *$Direction* and *$Key* second.
Only this client states *CCPM* in *$Supports* of the client to client handshake, on connections with TLS; the hub passes requests with *P* only between users that have the extension, so it needs no flag of the other client.
Connections for files never have it, so clients without this extension never see it.
It takes only the nick the hub named as sender, and states:

====
 $Direction PM 5678|
====

The client that waits for the connection takes *PM* only from a user it asked for a channel or whose request with *P* it answered a moment ago, and only over TLS, otherwise it closes the connection.
When it takes the channel, it confirms at once with a single *|*, and the connecting client opens the channel only after this confirmation.
*PM* is taken over its own direction, a download it wanted goes over another connection.
When two channels between the same users open at the same time, both clients keep the one that the user with the higher nick in byte order connected, and close the other.
A client that gets *PM* on a connection without TLS sends an error and closes it:

====
 $Error CCPM needs TLS|
====

Full example, *peter* is active and wants to chat with *john*:

====
 peter -> hub   $ConnectToMe john 192.168.1.3:412PS|
 hub -> john    $ConnectToMe john 192.168.1.3:412PS peter|
 john -> peter  $MyNick john|$Lock EXTENDEDPROTOCOLABCABCABCABCABCABC Pk=FearDC2.0.0.0|
 peter -> john  $MyNick peter|$Lock EXTENDEDPROTOCOLABCABCABCABCABCABC Pk=FearDC2.0.0.0|$Supports MiniSlots XmlBZList ADCGet TTHL TTHF ZLIG |$Direction Upload 1234|$Key ...|
 john -> peter  $Supports MiniSlots XmlBZList ADCGet TTHL TTHF ZLIG CCPM |$Direction PM 5678|$Key ...|
 peter -> john  |
====

When *peter* is passive, *john* answers *$RevConnectToMe peter john P* with *$ConnectToMe peter 192.168.1.4:413PS*, the hub adds *john*, *peter* connects and states *PM*.

A channel is a connection like any other for the *FDCX* extension: a client that shares an address states *FDCX* in its *$Supports* there too, and when both stated it, each sends its address with *$FDCX* once right after the confirmation, its certificate on the channel shows the keyprint.
A channel lives long, so a client tells its address again on the channel when it changes, and *$FDCX* without address when it stops sharing one, each one replaces the one before; a client that gets an address while it did not send its own yet answers with its own.
A client that checks the address of a user it has a channel with takes the last one of the channel, it needs no other connection for it.

After the confirmation both send messages, the sender is the other end of the connection:

====
 $MSG Hello john, how are you?|
====

Text is UTF-8 on a channel, also on hubs with another encoding, with *$* and *|* escaped as *&#36;* and *&#124;* like in chat.
A client sends a single *|* every few minutes so a dead channel is noticed, and either client closes the channel by closing the connection.
Commands for shared files are not allowed on a channel, a client answers them with *$Error* and closes it.
The hub does not see the messages.

Files of a chat, like pictures and voice messages, go over the channel in place of a magnet link, up to 10 MiB each.
The sender offers a file with its TTH, size and name, the name escaped like a message:

====
 $FILE TTHROOT 34567 picture.jpg|
====

The receiver shows it like a magnet link of the sender and asks for it when its user wants the file:

====
 $FILEGET TTHROOT|
====

The sender sends the file in pieces of at most 64 KiB, each piece is the command and then exactly that many raw bytes; messages can go between pieces:

====
 $FILEDATA TTHROOT 0 34567|<34567 bytes>
====

Pieces come in order, the receiver takes them only for a file it asked for and checks the TTH of the whole file.
The receiver asks for the next file of a channel only when the one before came or failed, so no file waits behind others.
A sender that can not give a file answers with a reason, *gone* when it is not offered any more, *busy* when too many files wait on the channel, *toobig* when it is larger than the limit:

====
 $FILENO TTHROOT gone|
====

When a file does not come over the channel, the receiver gets it from the sender like a file of a magnet link, through the hub.

Between two passive users over IPv4 with *NAT*, both ends use the ports of their hub connections, so only one connection between them fits.
When a file transfer between them needs these ports, the client that starts it asks the other one to give up the channel:

====
 $Close transfer|
====

The other client drops the connection at once without the closing wait of TCP, so the ports are free on both sides; when it does not do so within a few seconds, the asking client drops it the same way.
Both clients keep the private chat and send its messages through the hub from then on.

Hubs known to support this extension: Verlihub

Clients known to support this extension: FearDC


==== Avatar

Contexts: Client -> Hub -> Client, Hub -> Client, Client -> Client

This feature is used to show a picture of each user and of the hub itself next to their names, like messengers do.
The hub passes only the hash of the picture of a user, the picture itself goes between clients.
Only users who state the flag get avatars, other clients never see them.

Add *Avatar* to the *$Supports* to indicate support for this.
The hub adds it to its own *$Supports* when client stated it and the hub has this feature turned on, otherwise the command from that client is unknown to the hub.
A client shall not send the command to a hub that did not state the flag, and shall ignore it from such a hub.

The client sends the TTH of its avatar picture, also again when the picture changes, or nothing after the command when the user removed it:

====
 $Avatar ZXOJ3CT5RY4WTQ3IPOGKXGHNRTVJ7FLX3SHMZ2Q|
 $Avatar |
====

The TTH is the Base32 of the tiger tree root of the picture file, 39 characters, in upper case.
The hub checks its form and disconnects a client that sends anything else.
The client can send it before its login ends, the hub keeps it and passes it on when user is in the list.
A client that did not send a TTH on this connection sends no empty command, the hub knows no avatar of it at login.

The hub adds the nick of the sender itself, so nobody can send an avatar for another user, and sends it to every user with this flag, the sender too.
Each user entry ends with *$$*, also a single one, so a client tells it from the avatar of the hub; no TTH after the nick means the user removed the avatar:

====
 $Avatar peter ZXOJ3CT5RY4WTQ3IPOGKXGHNRTVJ7FLX3SHMZ2Q$$|
 $Avatar peter$$|
====

After login the hub sends the TTHs of all other users that have one in one command, like the *$UserIP* list:

====
 $Avatar peter ZXOJ3CT5RY4WTQ3IPOGKXGHNRTVJ7FLX3SHMZ2Q$$john 2SZHDJ6LV5YRUMH4UUTLGNLNKAMJMCYSWOUH6EI$$|
====

The command can come before *$MyINFO* of that nick, so a client keeps it until the user is known.
A hub may limit how often a user sends the command.

The hub tells its own avatar as the address of a picture without *$$*, "http://" or "https://" only, the same picture it gives to pingers with *$SetIcon*.
Nothing after the command means the hub has no avatar any more:

====
 $Avatar https://www.example.com/images/myicon.png|
 $Avatar |
====

The hub sends it after login when it has one, and again to every user with this flag when it changes.
A client gets the picture from that address itself, keeps it by its address and should give up after a few tries.

A client gets the picture of a user from the client of that user by its TTH, like any file, over a usual client to client connection asked with *$ConnectToMe* or *$RevConnectToMe*:

====
 $ADCGET file TTH/ZXOJ3CT5RY4WTQ3IPOGKXGHNRTVJ7FLX3SHMZ2Q 0 -1|
====

A client that states the flag to the hub gives its own avatar picture to anyone who asks for its TTH, without a free slot, also when the picture is not in its share.
The client that asks checks the TTH of the bytes it got and keeps the picture by its TTH, so a picture is got only once, also when many users have the same one.
An avatar picture is a small JPEG, PNG, GIF, WebP, BMP or ICO file of at most 64 KiB, a client ignores a bigger one or one it can not read.
A client shows the picture in a circle, so a square one fits best.
A client should get avatars without delaying other transfers, a few at a time, and give up after a few tries.

Hubs known to support this extension: Verlihub

Clients known to support this extension: FearDC

==== FailOver

Contexts: Hub -> Client

State: Both

====
 $FailOver [_host1[,_host2]]|
====

This feature is used to indicate support for providing alternative hub addresses in the event that the hub is unavailable.
See https://dc-protocols.github.io/ADC-EXT.html#_fo_failover_hub_addresses[ADC-Ext FO] for further information on the ADC equivalent.

It uses a comma (,) to separate hub addresses.

The command can be sent at any time by the hub, overwriting or replacing the addresses of the previous command.
An empty command (no hosts) clears the list of alternative addresses.

Add *FailOver* to the *$Supports* to indicate support for this.

|$Supports FailOver\| |
|$ValidateNick john\| |
| |$Supports FailOver\|
| |$Hello john\|
| |$FailOver hub.example.com:412\|
|=====

==== NickRule

Contexts: Hub -> Client, Hub -> Pinger

State: Handshake

====
 $NickRule [_rule1][$$_rule2]|
 $BadNick _rule1|
====

This extension specifies "+++$$+++" delimited list of nick rules currently being used by hub configuration for guest profile.

The command, if supported, is sent from hub to client right before the nick is about to be validated:

[options="autowidth,header"]
|=====
|Client|Hub
|$Supports NickRule\| |
| |$Supports NickRule\|
| |$NickRule Min 3+++$$+++Max 64+++$$+++Char 32 60 62+++$$+++Pref [ISP1] [ISP2]\|
|$ValidateNick [ISP1]john\| |
| |$Hello [ISP1]john\|
|=====

*Min* specifies minimum nick length.

*Max* specifies maximum nick length.

*Char* specifies space separated list of decimals forbidden to use in nick.

*Pref* specifies space separated list of nick prefixes required for usage on the hub.

Not all of the above parameters must be specified, the list is based on hub configuration.

Client has a chance to automatically update its nick before sending *$ValidateNick* command, if possible.
This applies only to clients who expect that used nick is not registered, e.g. when a password is not stored in favorites.

Clients that support *NickRule* but send invalid nick anyway, will receive *$BadNick* command with an error specification.

Nick is too short:

====
 $BadNick Min 3|
====

Nick is too long:

====
 $BadNick Max 64|
====

Bad characters found in nick:

====
 $BadNick Char 60 62|
====

Bad prefix found in nick:

====
 $BadNick Pref|
====

One of prefixes are required in nick:

====
 $BadNick Pref [ISP1] [ISP2]|
====

Client should then automatically correct its nick and reconnect to the hub, if possible.

Meaning of this extension is to avoid useless reconnects when nick rules are heavily restricted.

This applies only to non registered nicks.

Add *NickRule* to the *$Supports* to indicate support for this.

Hubs known to support this extension: Verlihub, FearHub

Clients known to support this extension: FearDC


==== SearchRule

Contexts: Hub -> Client, Hub -> Pinger

State: Handshake

====
 $SearchRule [_rule1][$$_rule2]|
====

This extension specifies "+++$$+++" delimited list of search rules currently being used by hub configuration.

The command, if supported, is sent from hub to client right after the nick validation:

[options="autowidth,header"]
|=====
|Client|Hub
|$Supports SearchRule\| |
|$ValidateNick john\| |
| |$Supports SearchRule\|
| |$Hello john\|
| |$SearchRule Min 3+++$$+++Max 256+++$$+++Num 1+++$$+++Int 4+++$$+++IntPas 6+++$$+++Share 10737418240\|
|=====

*Min* specifies minimum search string length.

*Max* specifies maximum search command length.

*Num* specifies number of searches available for use during a period of time.

*Int* specifies the period itself in seconds for active search requests for current user profile.

*IntPas* specifies the period in seconds for passive search requests for current user profile.

*Share* specifies minimum share size in bytes required for search for current user profile.

Not all of the above parameters must be specified, the list is based on hub configuration.
Client has a chance to automatically update its search interval settings for each hub, compare its share size with required size and prepare other kind of actions before sending any search request commands.

*Int* and *IntPas* might be set to zero "0" - which means that user is actually allowed to search without time limit, and might be set to "-1" - which means that user is not allowed to use search at all due to low profile or any other kind of restrictions.

Meaning of this extension is to avoid useless search requests to the hub, which are not going to bring any search results to the user anyway.
Atleast the user will know the reason of search results not appearing for him on a specific hub.

Hublist pingers can use this information to display on hub information page.

Add *SearchRule* to the *$Supports* to indicate support for this.

Hubs known to support this extension: Verlihub, FearHub

Clients known to support this extension: FearDC


==== HubURL

Contexts: Hub -> Client -> Hub, Hub -> Pinger -> Hub

State: Handshake

====
 $GetHubURL|
 $MyHubURL _url|
====

This extension allows the client to display hub URL currently being used for connection to the hub.

The hub, if supported, sends following request to the client anytime during the handshake:

[options="autowidth,header"]
|=====
|Client|Hub
|$Supports HubURL\| |
|$ValidateNick john\| |
| |$Supports HubURL\|
| |$Hello john\|
| |$GetHubURL\|
|$MyHubURL example.com:411\| |
| |$To: john From: Verlihub $<Verlihub> Please change the URL used to connect to this hub: hub.example.com:412\|
| |$ForceMove hub.example.com:412\|
|=====

Client should not spend any resources parsing the URL, it is enough to use the "getHubUrl()" method as is (see https://sourceforge.net/p/dcplusplus/code/ci/default/tree/dcpp/Client.h[DC++ source]).

Meaning of this extension is to collect statistics about hub addresses being used in a hub by its users, also to extend address checking functionality to redirect users to preferable hub address or port.

The idea was also to implement *$SetHubURL* command to specify preferable hub address without need to reconnect to the hub, in case it was accessed from hub favorites list.
We are hoping to finish this last part of the implementation very soon.

Add *HubURL* to the *$Supports* to indicate support for this.

Hubs known to support this extension: Verlihub, FearHub

Clients known to support this extension: FearDC


==== QuickList

The terms NDC and NHUB are used to denote a client or hub not featuring *QuickList* and QDC and QHUB for those that do.
The term DC is used when the type is not yet established or of no importance.
EACH and ALL signals that a message is sent N times, one message for each connected user.
Also note that the terms IF, MAY, SHOULD and MUST, have the same meaning as in the internet RFC specs.

Walkthrough
Connecting

[options="autowidth"]
|=====
|A DC connects to QHUB and does nothing
|QHUB sends $Lock which starts with "EXTENDEDPROTOCOL"
|QHUB also sends $HubName
|A DC must send $Key
|A DC may also send $Supports QuickList\| to signal in is in fact a QDC
|QHUB responds with $Supports QuickList\|
|=====

Identification

[options="autowidth"]
|=====
|A QDC may but should not send $Version
|A QDC must send $MyINFO
|=====

Authentication

[options="autowidth"]
|=====
|QHUB may send $GetPass
|QDC responds with $MyPass
|QHUB may send $BadPass and disconnect
|QHUB may send $ValidateDenide and disconnect
|=====

Acceptance

[options="autowidth"]
|=====
|QHUB may send $LogedIn to signal that H: should not be incremented
|QHUB sends all clients MyINFO to the QDC
|QHUB sends $OpList to the QDC
|QHUB may send $Hello to all clients but should send it to non QDC only
|QHUB sends $MyINFO to all QDC clients
|=====

Explanation
Connecting

This part has been through some changes.
There was an argument of having the client start with *$Supports* and then having the hub respond to that.
Having the client start with *$Supports* as a response to "EXTENDEDPROTOCOL" is in a sense much cleaner.

* It has been found that *$HubName* can be sent pretty much at any time. Typically done in conjunction with *$Lock*.
* *$Supports* are in the same format as in the client protocol; "$Supports <feat1> <feat2> <feat3>"

Identification

* Sending *$MyPass* early has been removed from the spec

Authentication

* As previously mentioned *$GetPass* is only sent if the user has an account and the *$MyPass* was not sent in the identification process. *$BadPass* or *$ValidateDenide* is sent when proper as usual.

Acceptance

From testing it has been found that *$Hello* and *$MyINFO* can be sent together without having to wait for a *$GetINFO*.

* Let the hub decide if the account should be treated as a VIP, i.e. not increment "H:" in the tag, hence it is not mandatory for accounts. A QDC should only respond to this message for account logins only.
* *$OpList* was missing

Commands Sent

Connecting

* *$Lock*
* *$HubName*
* *$Supports*

Identification
Authentication

* *$GetPass*
* *$BadPass*
* *$ValidateDenide*

Acceptance

* *$LogedIn*
* *$MyINFO*
* *$MyINFO* stream

Connected

* *$To:*
* *$Search*
* *$SR*
* *$ConnectToMe*
* *$RevConnectToMe*
* *$ForceMove*

Commands Accepted

Messages that a QHUB listens to in each state, QHUB ignores otherwise;

Connecting

* *$Key*
* *$Supports*

Identification

* *$Version*
* *$MyINFO*

Authentication

* *$MyPass*

Acceptance
Connected

* *$GetNickList*
* *$MyINFO*
* *$To:*
* *$Search*
* *$SR*
* *$ConnectToMe*
* *$RevConnectToMe*
* *$Kick*
* *$OpForceMove*

Notes

* *$ValidateNick* deprecated and ignored
* *$GetNickList* only valid when connected, a QDC does not receive a *$NickList*, but a series of *$MyINFO* directly
* *$Hello* deprecated and ignored
* *$GetINFO* deprecated and ignored
* *$MyINFO* is always accepted as valid and denotes a new or updated client

| |$OpList Verlihub+++$$+++OpChat+++$$+++\|
| |<MOTD> This is the MOTD message.\|
|=====
